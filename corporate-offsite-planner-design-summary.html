Overview

This example implements a supervisor / multi-agent pattern using LangChain's create_agent. A coordinator agent (the "planner") is given a set of tools, three of which are thin wrappers around three independent specialist sub-agents: a vision-based venue scout, a vision-based catering scout, and a text-based agenda writer. The coordinator decides when to call each tool, accumulates results, and synthesizes a final proposal.

All four LLMs are created from OpenRouter models via init_chat_model, with per-agent temperature/token/prompt configuration loaded from markdown+YAML prompt templates. This mirrors the simpler patterns shown in simple_agent.py and advanced_agent.py, scaled up to an orchestrated multi-agent workflow.

Step 1 Model Configuration init_chat_model

Each agent's LLM is described by a small ModelConfig dataclass (name, temperature, max_tokens, top_p, penalties, seed), populated from environment variables so behavior can be tuned per-agent without code changes. 

from langchain.chat_models import BaseChatModel, init_chat_model

def get_openrouter_model(config: ModelConfigLike, api_key: str) -> BaseChatModel:
    """Create an OpenRouter chat model from a model configuration."""
    params: dict[str, Any] = {
        "model": config.name,
        "model_provider": "openrouter",
        "api_key": api_key,
        "temperature": config.temperature,
        "max_tokens": config.max_tokens,
    }
    if config.top_p is not None:
        params["top_p"] = config.top_p
    # ... frequency_penalty, presence_penalty, seed appended the same way
    return init_chat_model(**params)
How it works: init_chat_model is LangChain's provider-agnostic model factory — passing model_provider="openrouter" lets a single call construct a chat model for any of OpenRouter's hosted models (GPT-OSS, Gemma vision, Poolside, etc.) with a uniform interface (BaseChatModel). Optional sampling parameters are only added when set, so provider defaults apply otherwise.
Why it matters: decoupling model selection from model usage means the same agent-building code works across OpenAI, Anthropic, OpenRouter, or local models — you only swap configuration, not logic. Per-agent tuning (e.g. low temperature for the vision scouts, higher for the planner's prose) is essential in multi-agent systems where each role needs different creativity/determinism trade-offs.

Step 2 Prompt Templates with Config Overrides

System prompts live in markdown files (resources/prompts/*.md) that embed a YAML front-matter block for model overrides, followed by a ## System prompt section:

## System prompt
You are a corporate offsite planner. First call update_state with the
destination, attendee_count and objective from the request. Once that
returns, delegate to your specialists: choose_venue and choose_catering
(vision scouts) and plan_agenda (agenda writer)...
def load_configured_model(
    prompt_name: str, base_config: ModelConfigLike, api_key: str
) -> tuple[str, BaseChatModel]:
    """Load a prompt and model, applying the prompt's configuration overrides."""
    system_prompt, overrides = load_prompt_template(prompt_name)
    model_config = replace(base_config, **overrides)  # dataclasses.replace
    return system_prompt, get_openrouter_model(model_config, api_key)
How it works: a regex extracts the fenced yaml block, parses it with yaml.safe_load, and applies it on top of a shared base ModelConfig via dataclasses.replace — only the fields present in the YAML are overridden.
Why it matters: keeping prompt text, its rationale, and its model tuning together in one reviewable file (versioned like code) is far more maintainable than scattering prompt strings and hyperparameters across Python source. It lets non-engineers iterate on prompts without touching application code.

Step 3 Building Agents with create_agent

Every agent — specialists and coordinator alike — is built with the same primitive: 

from langchain.agents import AgentState, create_agent

venue_prompt, venue_model = load_configured_model("venue_agent", VISION_CONFIG, openrouter_api_key)
venue_agent = create_agent(model=venue_model, system_prompt=venue_prompt)

coordinator_prompt, coordinator_model = load_configured_model("coordinator", PLANNER_CONFIG, openrouter_api_key)
offsite_tools = create_offsite_tools(venue_agent, catering_agent, agenda_agent, IMAGE_PATHS)

coordinator = create_agent(
    model=coordinator_model,
    tools=offsite_tools,
    state_schema=OffsiteState,
    system_prompt=coordinator_prompt,
)
How it works: create_agent builds a LangGraph-backed ReAct-style agent runnable: it loops the model over tool calls until the model produces a final text answer (or a recursion limit is hit). Specialist agents have no tools, so they always answer directly after one model call; the coordinator has tools, so it plans, calls tools, and reasons over their outputs.
Why it matters: this single abstraction removes the need to hand-roll a LangGraph state machine for the common "model + tools + system prompt" agent shape, while still returning a composable Runnable that can itself be wrapped as a tool for a parent agent (see Step 8) — enabling agent-of-agents architectures with minimal boilerplate.

Step 4 Extending Agent State 

class OffsiteState(AgentState):
    destination: str
    attendee_count: str
    objective: str
How it works: AgentState is a TypedDict-like schema that always includes messages; subclassing it adds extra typed fields that persist across the agent's tool-calling loop and are readable/writable by tools via runtime.state. Passing state_schema=OffsiteState to create_agent wires this custom schema into the underlying LangGraph graph.
Why it matters: plain conversational memory (messages) isn't enough once tools need structured data (destination, attendee count, objective) computed earlier in the run. Typed state gives tools a reliable, explicit "scratchpad" instead of re-parsing free text from prior messages.

Step 5 Tools with ToolRuntime 

from langchain.tools import ToolRuntime, tool

@tool
def choose_venue(runtime: ToolRuntime) -> str:
    """Review venue photos and recommend the best plus an alternative."""
    destination = runtime.state.get("destination", "the destination")
    ...
How it works: the @tool decorator turns a plain function into a LangChain BaseTool, inferring its schema from type hints and using the docstring as the tool description the LLM sees. Declaring a ToolRuntime-typed parameter gives the tool implicit access to the current agent state, context, and tool_call_id — without the model ever having to pass these as arguments.
Why it matters: this keeps the tool's public argument surface (what the LLM must supply) minimal and clean, while still letting the tool read privileged, non-hallucinatable data (like state set by an earlier tool call) directly and safely.

Step 6 Updating State with Command 

from langgraph.types import Command

@tool
def update_state(
    destination: str, attendee_count: str, objective: str, runtime: ToolRuntime,
) -> Command:
    """Record the destination, attendee count, and objective in agent state."""
    return Command(
        update={
            "destination": destination,
            "attendee_count": attendee_count,
            "objective": objective,
            "messages": [
                ToolMessage(content="Successfully recorded offsite details.",
                            tool_call_id=runtime.tool_call_id)
            ],
        }
    )
How it works: instead of returning a plain string, a tool can return a LangGraph Command whose update dict is merged directly into the graph state — here writing the three OffsiteState fields and appending the required ToolMessage (matched to the call via tool_call_id) in one atomic step.
Why it matters: this is the canonical, race-free way for a tool to both respond to the model and mutate shared agent state in a single graph transition — avoiding ad-hoc side channels or global variables, and keeping state changes auditable in the message/state history.

Step 7 Multi-modal (Vision) Tool Input 

content: list[Any] = [
    {"type": "text", "text": f"Review these candidate offsite venues in {destination}..."},
    {"type": "text", "text": "Option A:"},
    image_content_block(image_paths["venue_good_1.jpg"]),
    {"type": "text", "text": "Option B:"},
    image_content_block(image_paths["venue_good_2.jpg"]),
    ...
]
response = venue_agent.invoke({"messages": [HumanMessage(content=content)]})
How it works: a HumanMessage content can be a list of typed content blocks (text and image parts, e.g. base64 data URLs built by image_content_block) instead of a plain string. The vision-capable model (Gemma) receives interleaved text/image parts and reasons over them like any multi-modal chat completion.
Why it matters: LangChain's unified message content-block format lets the same create_agent/invoke call sites handle text-only and multi-modal models interchangeably — critical when composing agents with different modalities (vision scouts vs. text agenda writer) into one system.

Step 8 Agents-as-Tools (Supervisor Pattern) 

def create_offsite_tools(venue_agent, catering_agent, agenda_agent, image_paths) -> list[Any]:
    @tool
    def choose_venue(runtime: ToolRuntime) -> str:
        ...
        response = venue_agent.invoke({"messages": [HumanMessage(content=content)]})
        return f"{response['messages'][-1].content}\n\n{legend}"

    @tool
    def plan_agenda(runtime: ToolRuntime) -> str:
        response = agenda_agent.invoke({"messages": [HumanMessage(content=query)]})
        return response["messages"][-1].content

    return [update_state, choose_venue, choose_catering, plan_agenda]
How it works: each specialist create_agent(...) result is itself a runnable graph; wrapping an .invoke(...) call inside a @tool function exposes that whole sub-agent to the coordinator as a single callable tool. The coordinator LLM never sees the specialists' internals — only a tool name, description, and a string result.
Why it matters: this is the core "agents calling agents" composition technique in LangChain/LangGraph. It lets you decompose a complex task (plan an offsite) into independently testable, independently prompted/tuned sub-agents, while giving the top-level model a simple flat tool-calling interface — the same pattern scales to many specialists without growing the coordinator's prompt complexity.

Step 9 Bounded Completion Loop & Recursion Limit 

config: RunnableConfig = {"tags": ["OFFSITE"], "recursion_limit": 40}

for attempt in range(1, MAX_COORDINATOR_ATTEMPTS + 1):
    response = coordinator.invoke(state, config=config)
    missing_tools, has_final_answer = _conversation_status(response["messages"])
    if not missing_tools and has_final_answer:
        return response
    if attempt == MAX_COORDINATOR_ATTEMPTS:
        raise RuntimeError(f"Coordinator did not complete after {attempt} attempts...")
    recovery_message = HumanMessage(content="Continue and complete the offsite plan. ...")
    state = {**response, "messages": [*response["messages"], recovery_message]}
How it works: recursion_limit caps how many graph steps a single invoke can take (guarding against infinite tool-calling loops). _conversation_status inspects the returned messages for the four REQUIRED_TOOL_NAMES and a non-truncated final AI message; if the run stopped early, a synthetic recovery HumanMessage is appended and the coordinator is re-invoked with the accumulated state — up to MAX_COORDINATOR_ATTEMPTS times.
Why it matters: LLM agents can stop prematurely (hit a token/step limit, forget a step) especially when orchestrating several tool calls. This resumable-completion pattern turns an unreliable single-shot invocation into a robust, self-correcting run without re-doing already-completed (and costly) specialist calls, since state and prior messages are preserved between attempts.

Step 10 Conversation Persistence & Logging 

response = _run_coordinator_to_completion(user_prompt)
conversation_path = save_conversation(user_prompt, response["messages"], CONVERSATIONS_DIR, IMAGE_PATHS)
logger.info("Conversation saved to %s", conversation_path)
How it works: the full message trace (human prompt, tool calls/results, final proposal) is serialized to a markdown file per run, while structured logging calls trace each coordinator attempt, missing tools, and completion status to both console and a log file.
Why it matters: multi-agent runs are hard to debug from stdout alone. Persisting the full conversation (including image legends) plus structured logs gives a reproducible audit trail for prompt iteration, regression comparison, and demoing the system's behavior.
