Javaslat

Az Anthropic és az OpenAI alapelveire épül

Ez a megoldás nem csak egy konkrét példa, hanem azt is bemutatja, milyen alapelvek mentén érdemes bármilyen LLM-alapú rendszert felépíteni:

1

Az LLM-nek nincs memóriája — teljesen "stateless". Minden egyes hívás önmagában áll: a modell semmire nem emlékszik a korábbi kérdésekből, amit nem adunk át neki újra.

2

Az LLM kétféleképpen kaphat információt: vagy a kérés részeként, az SDK-nak elküldött JSON adatban, vagy egy funkció (tool) meghívásával, amit a modell maga kér le, amikor szüksége van rá.

3

Minél több információt adunk át az LLM-nek, annál nagyobb a tokenhasználat és a bizonytalanság. Ezért csak azt az információt kapja meg, amire az adott lépésben valóban szükség van.

4

Minden LLM-hívás előtt és után guardrailt kell használni. A modell válasza önmagában nem garancia — ezért minden hívás előtt és után egy megbízható, kódban megírt ellenőrzés fut, amire a rendszer biztonsága épül.

Alapelvek részletesen

Agentic architektúra és orkesztráció

A fenti négy alapelv az agentic architektúrára és orkesztrációra épül. Következetesen a determinisztikus, kontrollált megoldásokat érdemes előnyben részesíteni a valószínűségi, "megérzésre" bízott megoldásokkal szemben.

1.1Agentic loop és az API alapjai

1

Az agentic loop többlépéses önálló végrehajtás. A Claude emberi beavatkozás nélkül hajt végre többlépéses feladatot: Terv → Cselekvés → Megfigyelés → Döntés → Ismétlés. A ciklus minden körben meghívja az Anthropic API-t.

2

A legfontosabb a ciklus kontrollja. A ciklus akkor ér véget, amikor az API-válaszban a stop_reason ezt jelzi. Nem a modell szövegét értelmezzük, hanem ezt a determinisztikus jelzést.

3

A tool eredményt mindig vissza kell fűzni. A következő API-hívás előtt a beszélgetés-előzményhez hozzá kell adni az assistant üzenetet (a tool_use kéréssel), majd egy új user üzenetet a tool eredményével.

stop_reasonJelentése a ciklusban
tool_useA modell tool-t kér: futtasd, fűzd vissza az eredményt, ismételj.
end_turnA modell végzett: a ciklus normálisan véget ér.
max_tokensA válasz a tokenkorlát miatt csonkult el.
stop_sequenceA modell egy előre megadott leállító szekvenciát generált.
pause_turnA hosszan futó kör szünetel: a beszélgetés folytatható.
refusalA modell biztonsági okból megtagadta a választ.
model_context_window_exceededA kontextusablak betelt.

1.2Multi-agent orkesztráció

1

Hub-and-spoke minta. Minden kommunikáció a központi orkesztrátoron (hub) megy keresztül; a sub-agentek soha nem beszélnek egymással. Előnyei: kontextus-izoláció, fókuszált tool-ok, párhuzamos végrehajtás és hibaizoláció.

2

A Task tool új, izolált agentet indít. Csak az orkesztrátor rendelkezik vele. Ha egyetlen válaszban több Task hívás szerepel, a sub-agentek párhuzamosan futnak; ha külön válaszokban, akkor szekvenciálisan.

3

Session-műveletek: resume és fork. A --resume egy meglévő sessiont folytat, mint egy commit a fő ágra. A fork session új sessiont hoz létre a teljes eddigi kontextussal, de függetlenül fut, és nem módosítja a szülőt, mint egy új ág Gitben.

1.3Hookok: programozott kikényszerítés

1

A hook determinisztikus kód a tool előtt és után. Futhat a tool hívása előtt (a paraméterek validálása, a művelet blokkolása) és után is. Üzleti szabályokra, megfelelőségre és biztonságra való, és azonnali hibát dob.

2

Ami 100%-ban kötelező, azt hookkal kell kikényszeríteni. A prompt alapú utasítás valószínűségi, ezért nem garancia. Ugyanez az elv áll a példa guardrail-rétege mögött.

Tipp: ha bizonytalan vagy, válaszd a legkontrolláltabb, legdeterminisztikusabb megoldást.
Megfeleltetés a példa megvalósításához: a fenti fogalmak a Claude API és a Claude Agent SDK nevei. A példa LangChain-nel és OpenAI modellekkel fut, ott a megfelelőik: hook → LangChain middleware (before_model / after_model), stop_reason → OpenAI finish_reason, Task tool (az Agent SDK-ban ma már Agent tool) → tool-ként becsomagolt subagent.

1.4Session-kezelés és munkafolyamat

1

Elavult kontextus csapdája. A session elején lekért adat a felhasználás idejére elavulhat. Védekezés: a kritikus adat újralekérése a felhasználás előtt, scratchpad fájlok a köztes állapothoz, TTL-t figyelő cache és checkpointok.

2

Prompt chaining: kiszámítható, lineáris feladatokra. A munkafolyamatot előre definiáljuk, a lépések sorrendje fix.

3

Dinamikus, adaptív: előre nem látható, eredményvezérelt feladatokra. Az agent maga dönt a következő lépésről. A kérdés: a következő lépést a terv vagy az eredmény határozza meg? Terv → chaining, eredmény → adaptív.

A felépítés az Anthropic alapelveire épül (Building effective agents): egyszerűen indulj, és csak akkor bonyolíts, ha a mérések indokolják. 1 · Egyetlen agent

Egy agent, minden funkcióval

A legegyszerűbb forma: egy agent kapja meg az összes funkciót, és maga dönt, melyiket hívja. Kevés funkciónál ez a legolcsóbb és legkönnyebben követhető megoldás.

Anthropic: a „bővített LLM” (eszközök + memória), illetve az önállóan döntő agent. OpenAI: single-agent rendszer: egy futtatási ciklus, a funkciókat fokozatosan adjuk hozzá.

2 · Router nélkül

Orchestrator és szakértő subagentek

Ha a funkciók száma és a prompt mérete nő, a feladatot szakterületek szerint szétosztjuk: az orchestrator subagenteket hív (akár párhuzamosan), és összeállítja a választ.

Anthropic: orchestrator-workers minta: a központi agent menet közben bontja részfeladatokra a kérdést. OpenAI: manager minta: a subagentek a manager eszközeiként hívódnak, a felhasználóval csak a manager beszél.

3 · Routerrel

Router, orchestrator, subagentek és összeállító

A legösszetettebb forma: a router előre eldönti, miről szól a kérdés és hozzáférhet-e a felhasználó. Jogosultság híján a kód rövidre zárja, az LLM-et meg sem hívja. Több subagent válaszát egy összeállító agent egyesíti.

Anthropic: routing workflow (a bemenetet besorolja, és szakosodott útra küldi) az orchestrator-workers előtt. OpenAI: a triage-agent / besorolás gondolata a manager mintával, plusz guardrail-ek, amelyek kódszinten kényszerítik ki a jogosultságot.
