Proposal

Built on the principles of Anthropic and OpenAI

This solution is not just one concrete example; it also shows the principles worth following when building any LLM-based system:

1

An LLM has no memory — it is completely "stateless". Every call stands on its own: the model remembers nothing from earlier questions unless we pass it again.

2

An LLM can receive information in two ways: either as part of the request, in the JSON data sent to the SDK, or by calling a function (tool) that the model itself asks for when it needs it.

3

The more information we pass to the LLM, the higher the token usage and the uncertainty. That is why it receives only the information that is really needed in the given step.

4

A guardrail must be used before and after every LLM call. The model's answer alone is no guarantee — so before and after every call a reliable check written in code runs, and the system's safety is built on it.

The principles in detail

Agentic architecture and orchestration

The four principles above rest on agentic architecture and orchestration. Deterministic, controlled solutions should consistently be preferred over probabilistic ones left to "gut feeling".

1.1The agentic loop and API basics

1

The agentic loop is autonomous multi-step execution. Claude carries out a multi-step task without human intervention: Plan → Act → Observe → Decide → Repeat. In every round the loop calls the Anthropic API.

2

Control of the loop matters most. The loop ends when the stop_reason in the API response says so. We do not interpret the model's text; we read this deterministic signal.

3

Always feed the tool result back. Before the next API call, add the assistant message (with the tool_use request) to the conversation history, then a new user message with the tool result.

stop_reasonMeaning in the loop
tool_useThe model requests a tool: run it, feed the result back, repeat.
end_turnThe model is done: the loop ends normally.
max_tokensThe answer was cut off by the token limit.
stop_sequenceThe model generated a predefined stop sequence.
pause_turnA long-running turn is paused: the conversation can continue.
refusalThe model declined to answer for safety reasons.
model_context_window_exceededThe context window is full.

1.2Multi-agent orchestration

1

Hub-and-spoke pattern. All communication goes through the central orchestrator (hub); sub-agents never talk to each other. Advantages: context isolation, focused tools, parallel execution and fault isolation.

2

The Task tool starts a new, isolated agent. Only the orchestrator has it. If several Task calls appear in a single response, the sub-agents run in parallel; in separate responses, sequentially.

3

Session operations: resume and fork. --resume continues an existing session, like a commit on the main branch. fork session creates a new session with the full context so far, but it runs independently and does not modify the parent, like a new branch in Git.

1.3Hooks: programmatic enforcement

1

A hook is deterministic code before and after a tool. It can run before the tool call (validate parameters, block the action) and after it. It is meant for business rules, compliance and security, and it fails immediately.

2

Whatever must hold 100% of the time is enforced with a hook. A prompt-based instruction is probabilistic, so it is no guarantee. The same principle stands behind the example's guardrail layer.

Tip: when in doubt, choose the most controlled, most deterministic solution.
Mapping to the example's implementation: the concepts above are the names used by the Claude API and the Claude Agent SDK. The example runs on LangChain with OpenAI models, where the equivalents are: hook → LangChain middleware (before_model / after_model), stop_reason → OpenAI finish_reason, Task tool (in the Agent SDK now called the Agent tool) → a subagent wrapped as a tool.

1.4Session management and workflow

1

The stale-context trap. Data fetched at the start of a session can be out of date by the time it is used. Defences: re-fetch critical data before use, scratchpad files for intermediate state, caches that watch their TTL, and checkpoints.

2

Prompt chaining: for predictable, linear tasks. The workflow is defined in advance and the order of steps is fixed.

3

Dynamic, adaptive: for unpredictable, result-driven tasks. The agent itself decides the next step. The question: is the next step determined by the plan or by the result? Plan → chaining, result → adaptive.

Full overview

Several paths lead to the answer: from the simple to the complex.

The structure builds on Anthropic's principles (Building effective agents): start simple, and add complexity only when measurements justify it. OpenAI's guide (A practical guide to building agents) says the same: a single agent first, and only then several agents. We show three variants with more and more parts, plus a fourth shape for web research; for each we point out the matching Anthropic and OpenAI pattern. In all of them, the answer passes through a response gateway written in code and through safety filters.

1 · Single agent

One agent, all functions

The simplest form: one agent receives all the functions and decides for itself which to call. With few functions this is the cheapest and easiest-to-follow solution.

Anthropic: the "augmented LLM" (tools + memory), or the autonomously deciding agent. OpenAI: a single-agent system: one run loop, functions are added gradually.

2 · No router

Orchestrator and expert subagents

When the number of functions and the prompt size grow, we split the task by domain: the orchestrator calls subagents (even in parallel) and assembles the answer.

Anthropic: the orchestrator-workers pattern: the central agent breaks the question into subtasks on the fly. OpenAI: the manager pattern: subagents are called as the manager's tools, and only the manager talks to the user.

3 · With a router

Router, orchestrator, subagents and synthesizer

The most complex form: the router decides in advance what the question is about and whether the user may access it. Without entitlement, the code short-circuits and the LLM is not even called. A synthesizer agent merges the answers of several subagents.

Anthropic: the routing workflow (classify the input and send it down a specialised path) in front of orchestrator-workers. OpenAI: the triage-agent / classification idea with the manager pattern, plus guardrails that enforce entitlement at code level.

4 · Web search

Search, parallel page readers and consolidation

A different shape for open questions: there is no router, no customer and no clarifying question. The agent searches DuckDuckGo at once, picks the three most relevant links and starts one subagent per link in parallel. It waits for all three summaries, then consolidates them into one answer with clickable links.

Anthropic: orchestrator-workers with a parallelization workflow (sectioning): the same task fanned out to independent workers and aggregated. OpenAI: the manager pattern with parallel tool calls; the fan-out and the wait for every worker are done in code, not left to the model.

One important rule, whichever structure you choose.

Whatever must hold 100% of the time is enforced by code, not by the model's goodwill: whose data is concerned, whether the user may access a function, and what reaches the operator. Models decide only where the decision really needs interpretation — and even there they are surrounded by safety filters.
