Eval Driven Development · R&D Harness Agent

The bank branch officer example is the architecture of a Bank Agent Harness Chat application, built on the Anthropic and OpenAI documentation. Today it is a fixed pipeline: the order of the router, the coordinator, the specialists and the guardrails is set by code. That is a good starting point, but "it works in the demo" does not tell us whether a change makes it better. With this example we present EDD: we organise the agent's development around an eval set, on the already working mock application as a POC.

Why adopt it?

Without measurement we fly blind. A prompt change can improve one type of question and silently break another, for example the entitlement handling of card limits.
The building block is probabilistic. The same question run three times can give three different answers, so it must be measured, not calculated.
The risk of a change becomes predictable. Before swapping a model, adding a specialist or rewriting a prompt, you can compare before and after on the same set, in days instead of weeks.
"Good" has to be defined. Instead of "an adequate answer": the number matches the test data, or the answer is refused because of entitlement.
Reliability is more than a one-off success. A rule that holds 9 times out of 10 is not a rule in production, so we run the same question several times (--repeat) and every run has to pass.

The POC in three steps: look at the working example

The three cards on the home page are also the three steps of the EDD process.

1 · the dynamic architecture

What can be swapped, and what stays in code?

The architecture is not fixed: the architecture page shows three variants, from the simple to the complex (a single agent, without a router, with a router), and they can be switched as profiles. EDD asks here:

  • What stays always in code? Entitlement, PII, query-only, a fixed answer on failure.
  • What can be changed based on measurement? Whether a router, delegation or a single agent is needed, which model, which prompt.
Architecture page →
2 · Test catalog

The test data is the yardstick

The data of the three mock customers and the REST endpoints behind them are the reference: from them you can work out in advance what the correct number is and what must be refused for a retail customer. In a mock environment an experiment is cheap and repeatable; on the live system it is expensive and risky.

3 · try it and measure

Chat, then eval

In the chat you can follow a question live: which endpoint the router hit, which tools the agent called, what came back after the guardrail. The eval page runs the same questions on several architecture profiles, so the comparison is a number, not an impression.
